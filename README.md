## 1. نظرة عامة

Book Mart تطبيق محلي لنقطة بيع وإدارة متجر، مبني باستخدام Flask وSQLite وواجهة عربية من اليمين إلى اليسار. يشمل البيع والمخزون والمشروبات والوصفات والكتب والمنتجات الإضافية، مع صفحات إدارية للموظفين والورديات والمصروفات والتقارير.

يعمل التطبيق على الجهاز المحلي ولا يحتاج إلى CDN أو تنزيل خطوط أو أي مورد من الإنترنت أثناء الاستخدام. يمكن تشغيله داخل نافذة سطح مكتب عبر PyWebView أو في المتصفح على عنوان محلي.

## 2. الميزات وسير العمل

### نقطة البيع

- افتح شاشة الكاشير من الصفحة الرئيسية، ثم اختر تصنيفًا أو ابحث عن منتج وأضفه إلى السلة.
- تتعامل السلة مع الكتب والمشروبات ومنتجات البيع بالتجزئة. تعرض تصنيفات المشروبات والتجزئة النشطة التي لها منتجات، كما تبقى المنتجات ذات التصنيف غير المعروف أو غير النشط متاحة تحت «الكل» والبحث. للكتب تبويب موحد.
- تُراجع الكميات المتاحة عند الإضافة إلى السلة ثم يعيد الخادم التحقق من المخزون والوصفات عند إتمام البيع. تُحفظ عملية البيع وتحديثات المخزون في معاملة SQLite واحدة؛ إذا فشل التحقق لا يُعتمد الطلب.
- يمكن إلغاء آخر عملية بيع، كما يوجد مسار إلغاء لطلب محدد. الإلغاء يحدّث حالة الطلب بدل حذف سجل البيع.
- الإيصال متاح من مسار الطباعة، ويستخدم وقت الطلب المسجل في قاعدة البيانات.
- يعرض شريط الكاشير إجمالي مبيعات اليوم فقط؛ لا يعرض بيانات الرواتب أو الحضور.

### الكتب والمشروبات والمواد ومنتجات التجزئة

- **الكتب:** سجّل العنوان والمؤلف والناشر الاختياري والنوع وسعر التكلفة والبيع والمخزون. قيم النوع المخزنة حرفيًا هي `Original` و`High Copy`. لا يوجد تنبيه إعادة طلب للكتب في لوحة المخزون.
- **المشروبات:** أنشئ المواد أولًا، ثم اربط كل مشروب بمقادير مواده من محرر الوصفة. تُحفظ الوصفة داخليًا في `recipe_json`، ويُحسب استهلاك المواد والتكلفة بناءً عليها عند البيع. المشروبات المزروعة مبدئيًا لها وصفة فارغة حتى تُضبط.
- **المواد:** تُدار تكلفة الوحدة والمخزون وحد إعادة الطلب. الوحدات القياسية المخزنة هي `g` و`kg` و`ml` و`L` و`pcs`، وتظهر للمستخدم بالعربية. لا يمكن تغيير وحدة مادة مستخدمة في وصفة مشروب لأن ذلك سيغيّر مقادير الوصفة. تُعرض المواد التي وصلت إلى حد إعادة الطلب في تنبيه المخزون المنخفض.
- **التجزئة:** تُدار المنتجات ذات المخزون المستقل، مثل المشروبات المعبأة والكوكيز والإضافات. تُخصم كمياتها عند البيع، ولا تُعامل الإضافات كخيارات مرتبطة بسطر مشروب في السلة.
- **التصنيفات:** تُدار تسميات التصنيفات وترتيبها وحالتها. قيمة `slug` معرّف داخلي ثابت؛ غيّر التسمية العربية بدلًا منه. قبل حذف تصنيف مستخدم، انقل المنتجات إلى تصنيف آخر.
- قد تُزرع بيانات أولية للمشروبات والتجزئة والكتب عند إنشاء قاعدة بيانات جديدة. تُستخدم مفاتيح البذر لمنع التكرار، ولا تستبدل تعديلات المدير على المنتجات الموجودة.

### الموظفون والورديات والماليات

- أنشئ حساب الموظف وحدد صلاحيات البيع وإدارة المصروفات والمشتريات والمخزون. صلاحية المشتريات موجودة في سجل الموظف، لكن لا توجد حاليًا واجهة API مخصصة لإضافة سجلات شراء.
- يسجّل الموظف الدخول من شاشة الكاشير؛ تُفتح له وردية ويُسجّل رصيد الدرج. عند استلام وردية مفتوحة من موظف آخر، يطلب النظام جرد الرصيد قبل التسليم.
- عند إنهاء الوردية يُدخل الموظف الرصيد المعدود؛ يسجل النظام ساعات العمل والمبلغ المستحق وفارق الدرج وسبب الإنهاء أو التسليم.
- تُدار المصروفات في البيانات الإدارية، وتظهر سجلات المشتريات والسجل النقدي عند وجودها في تقارير المشروع. تُعرض تسويات الرواتب الشهرية في صفحة الرواتب، ويُسجّل الدفع لكل موظف وشهر مرة واحدة.
- صفحة الحضور مبنية على سجلات الورديات، وليست على جدول حضور منفصل.

### لوحة المعلومات والتقارير ويوم العمل

- تعرض لوحة المدير مبيعات اليوم، والأرباح المحسوبة من المبيعات ناقص تكلفة البضاعة المباعة والمصروفات، وعدد الفواتير وآخر عملية بيع، إلى جانب قائمة انخفاض مخزون المواد.
- ملخص «مبيعات اليوم» يستخدم `business_date_for`: يبدأ يوم التقرير عند الساعة 10:00 محليًا، لذلك تُنسب عملية الساعة 01:00 إلى يوم العمل السابق. هذا حدّ لتجميع ملخص المبيعات، وليس ضبطًا لساعات فتح التطبيق أو إغلاقه، ولا يوجد عمود مستقل باسم `business_date` في جدول الطلبات.
- التقرير الشهري في `/api/admin/reports` يجمع حسب الشهر التقويمي لتاريخ الطلب والمصروف.
- **اختلاف مهم:** تقارير المشاريع اليومية (`/api/projects/report` و`/api/admin/projects/report`) تعتمد تاريخ اليوم التقويمي/تاريخ المشروع، ولا تطبق حدّ الساعة 10:00 نفسه. لا ينبغي اعتبار كل التقارير اليومية متطابقة مع يوم ملخص لوحة المعلومات.

### الإعدادات والطباعة والاستيراد

- إعدادات المدير تشمل اسم المتجر وعنوانه وعدد ساعات الوردية. يُستخدم اسم المتجر الحالي في الواجهات ورؤوس الطباعة؛ لا توجد إعدادات ثيم ديناميكي.
- تتوفر قوالب واستيراد للكتب والمواد والمشروبات والتجزئة. تقبل الاستيرادات ملفات CSV وXLS وXLSX وXLSB، وتُعالج حتى 1000 صف؛ تُعاد أخطاء الصفوف مع عدد الصفوف المستوردة. قد تُحفظ الصفوف الصحيحة حتى عند وجود صفوف فاشلة.
- يعرض مسار الإيصال صفحة طباعة بعرض CSS قدره 280px وخط عربي/نظامي. لا يوجد اختيار صريح بين مقاسي 58mm و80mm، والخط ليس monospace.

## 3. متطلبات التشغيل

- **نظام التشغيل المستهدف للنشر:** Windows 7 SP1 أو أحدث. توافق نافذة PyWebView يعتمد أيضًا على توفر مكوّنات العرض المناسبة على الجهاز.
- **Python:** الإصدار 3.9، ونسخة 32-bit عند الاستهداف على Windows 7 ذي 32-bit. لا يمكن بناء ملف Windows تنفيذي من نظام تشغيل أو معمارية مختلفة.
- **الحزم:** الإصدارات المثبتة في `requirements.txt` هي Flask 3.1.3 وWerkzeug 3.1.9 وPyWebView 4.4.1 وOpenPyXL 3.1.5 وxlrd 2.0.1 وpyxlsb 1.0.10، إضافة إلى PyInstaller.
- قد يتطلب PyWebView على بعض أجهزة Windows تثبيت Microsoft Visual C++ Runtime وWebView2 Runtime المناسبين. اختبر نافذة العرض على جهاز النشر قبل الاعتماد عليها.
- لا توجد خطوط مضمّنة في `static/fonts`؛ تستخدم الواجهة خطوط النظام. شعار `static/img/logo.png` اختياري، ويُستعاض عنه بالعلامة النصية إن لم يوجد.
- لا يحتاج التشغيل اليومي إلى اتصال إنترنت. يلزم الوصول إلى الإنترنت فقط لتنزيل Python والحزم أو أدوات البناء أثناء التجهيز.

## 5. التثبيت من المصدر

ثبّت Python 3.9 بالمعمارية المناسبة، ثم افتح PowerShell أو موجه الأوامر في مجلد المشروع:

```bat
py -3.9-32 -m venv .venv
.venv\Scripts\activate
python -m pip install --upgrade pip
pip install -r requirements.txt
```

إذا كان Python 3.9 المثبت 64-bit، استخدم مشغّل تلك النسخة بدل `py -3.9-32`، مع العلم أن ذلك لا يجعلها مناسبة للتشغيل على Windows ذي 32-bit.

## 6. التشغيل

```bat
python app.py
```

هذا هو وضع سطح المكتب: يبدأ خادمًا محليًا على منفذ متاح، ثم يحاول فتحه في نافذة PyWebView. إذا لم تكن PyWebView قابلة للاستيراد، يسجل التطبيق تحذيرًا ويفتح عنوان التطبيق المحلي في المتصفح الافتراضي.

لتشغيل وضع المتصفح يدويًا:

```bat
python app.py --web
```

ثم افتح `http://127.0.0.1:5000`. هذا الوضع مربوط بعنوان loopback ولا يفتح الخادم على واجهة الشبكة. لا يعمل Flask في هذا المسار مع وضع التصحيح أو إعادة التحميل التلقائي.

### أول دخول

عند إنشاء قاعدة بيانات جديدة، تُضاف حسابات المدير الابتدائية بطريقة لا تستبدل حسابًا موجودًا:

- اسم المستخدم: `admin`
- كلمة المرور: `123456`

غيّر كلمة المرور فورًا بعد تسجيل الدخول. لا تستخدم بيانات الدخول الافتراضية في بيئة فعلية.

## 7. التشغيل التلقائي مع Windows

بعد بناء الملف التنفيذي، أنشئ اختصارًا إلى `dist\BookMart.exe` وضعه في مجلد بدء التشغيل للمستخدم:

1. اضغط `Win+R`.
2. اكتب `shell:startup` ثم اضغط Enter.
3. انسخ الاختصار إلى المجلد المفتوح.

يعتمد بدء التشغيل على تسجيل دخول المستخدم؛ ولا يحوّل التطبيق إلى خدمة Windows.

## 8. بناء ملف تنفيذي

ابنِ على Windows باستخدام Python 3.9 المطابق لمعمارية جهاز النشر. من مجلد المشروع وبعد تفعيل البيئة الافتراضية:

```bat
pyinstaller --noconfirm --clean --onefile --windowed --name "BookMart" --add-data "templates;templates" --add-data "static;static" --collect-all webview app.py
```

ينتج الملف في `dist\BookMart.exe`. يتضمن `static` الشعار إن كان موجودًا؛ لا يوجد مجلد خطوط مضمّنة. أنشئ الملف على Windows ومعمارية Python المستهدفة، ثم اختبره على جهاز التوزيع ومكوّنات PyWebView المتوفرة عليه. تحفظ قاعدة البيانات خارج الملف التنفيذي في مجلد بيانات المستخدم.

## 9. قاعدة البيانات والترقيات

### موقع البيانات

يُحفظ `database.db` في المسار التالي، حسب الأولوية:

1. المسار المحدد في متغير البيئة `BOOK_MART_DATA_DIR`.
2. `%LOCALAPPDATA%\BookMart` على Windows.
3. مجلد التطبيق إذا لم يتوفر `LOCALAPPDATA`.

أما القوالب والملفات الثابتة فتُحلّ عبر `resource_path` لتعمل من المصدر ومن حزمة PyInstaller.

### الجداول والأعمدة

تُنشأ الجداول باستخدام `CREATE TABLE IF NOT EXISTS`. هذه قائمة أسماء الأعمدة التي يعرّفها المخطط الحالي:

| `users` | `id`, `username`, `password_hash`, `role` |

| `business_days` | `id`, `project_date`, `opening_cash`, `status`, `created_at`, `closed_at`, `expected_cash`, `counted_cash`, `closing_variance` |

| `cash_entries` | `id`, `business_day_id`, `shift_id`, `employee_id`, `entry_type`, `amount`, `category`, `reference_type`, `reference_id`, `description`, `created_at` |
| `purchases` | `id`, `business_day_id`, `shift_id`, `employee_id`, `timestamp`, `supplier`, `category`, `amount`, `items_json`, `note` |
| `payroll_settlements` | `id`, `employee_id`, `month`, `monthly_salary`, `worked_seconds`, `scheduled_seconds`, `completed_shifts`, `amount`, `paid_at` |

### التهيئة والترقية

- يهيئ التطبيق قاعدة البيانات عند بدء التشغيل، ويستخدم `PRAGMA table_info` للتحقق من الأعمدة وإضافة ترقيات متوافقة عند الحاجة.
- تزرع فئات وبيانات كتالوج أولية دون تكرار مفاتيح البذر أو الكتابة فوق التعديلات الموجودة.
- تتضمن التهيئة تحويلات متوافقة لمخزون قديم، منها نقل بعض صفوف الكتب التي تمثل منتجات تجزئة إلى جدول `retail`، وتوحيد بعض التصنيفات وأنواع الكتب.
- خذ نسخة احتياطية قبل تشغيل إصدار جديد على قاعدة بيانات إنتاجية. التهيئة التلقائية لا تغني عن النسخ الاحتياطي.

## 10. واجهات API

تستخدم الواجهات JSON حيث يلائم ذلك. مسارات `/api/admin/...` المحمية تتطلب جلسة مدير، وتُقيّد بعض عمليات المخزون والمصروفات بصلاحيات الموظف المناسبة. صفحات الإدارة لا تمنح صلاحيات لمجرد إخفاء عنصر من الواجهة؛ الخادم يتحقق من الجلسة والصلاحية. يوضح الجدول الغرض وشكلًا مختصرًا للمدخلات أو النتائج، وليس مخطط JSON كاملًا لكل حقل.

| الطريقة والمسار | الوصول | الغرض والمدخلات/النتائج الرئيسية |
|---|---|---|
| `GET /` | شاشة الكاشير | يعرض صفحة البيع ويهيئ جلسة الكاشير. |
| `GET /admin/login`, `POST /admin/login` | تسجيل مدير | يعرض النموذج؛ يستقبل `username` و`password` كبيانات نموذج، ثم ينشئ جلسة المدير أو يعرض خطأ تسجيل الدخول. |
| `POST /admin/logout` | جلسة المدير | ينهي جلسة المدير ويعيد المستخدم إلى الكاشير. |
| `GET /admin` | مدير أو موظف مخوّل | يعرض لوحة الإدارة والصفحة الابتدائية المسموح بها. |
| `POST /api/employee/login` | تسجيل موظف | يستقبل بيانات JSON لتسجيل الدخول، وقد يستقبل `counted_cash` عند استلام وردية؛ يعيد بيانات الموظف والوردية أو معلومات طلب التسليم. |
| `POST /api/employee/logout`, `GET /api/employee/current` | لا يشترطان جلسة لطلب المسار؛ تُعاد بيانات الموظف عند وجود جلسة صالحة | إنهاء الجلسة أو قراءة حالة الموظف والوردية والدرج الحالي. |
| `POST /api/employee/shift/close` | جلسة الموظف | إغلاق الوردية مع الرصيد المعدود وبيانات الإنهاء أو التسليم. |

## 11. النسخ الاحتياطي والاستعادة

1. أغلق التطبيق قبل نسخ قاعدة البيانات.
2. انسخ ملف `database.db` من مجلد البيانات الفعلي. افتراضيًا على Windows هو `%LOCALAPPDATA%\BookMart`؛ إذا ضُبط `BOOK_MART_DATA_DIR` فالمسار المحدد فيه هو المستخدم.
3. احتفظ بنسخة مؤرخة في وسيط آمن، ولا تضع النسخة الوحيدة بجانب الملف التنفيذي.
4. للاستعادة، أوقف التطبيق، احتفظ بنسخة من قاعدة البيانات الحالية، ثم ضع النسخة الاحتياطية باسم `database.db` في مجلد البيانات الصحيح وأعد التشغيل.

ينبغي اختبار الاستعادة دوريًا. نسخ قاعدة البيانات أثناء الكتابة قد ينتج نسخة غير متسقة؛ لذلك أوقف التطبيق أولًا.

## 12. الأمان والقيود المعروفة

- غيّر كلمة مرور المدير الافتراضية مباشرة. كلمة المرور تُحفظ كقيمة تجزئة، وليس كنص صريح.
- يخزن التطبيق مفتاح جلسة Flask في جدول الإعدادات. احمِ مجلد البيانات والملف التنفيذي من وصول غير المخولين.
- جلسة Flask تستخدم خصائص `HttpOnly` و`SameSite=Lax`. صلاحيات المدير والموظف تتحقق على الخادم، لكن التطبيق مصمم للاستخدام المحلي وليس كخدمة مكشوفة على شبكة عامة.
- بعض المسارات التي تستخدمها شاشة الكاشير، ومنها قائمة المنتجات وإنشاء الطلب وملخص مبيعات اليوم والتصنيفات النشطة وطباعة الإيصال، لا تفرض حارس جلسة صريحًا على المسار نفسه؛ الصفحة الرئيسية تهيئ جلسة الاستخدام المعتادة، لكن ذلك ليس بديلًا عن مصادقة API. لا تعرّض هذه المسارات خارج الجهاز المحلي.
- معاملات SQL الخاصة بالقيم تستخدم معاملات SQLite؛ أسماء الجداول الديناميكية محصورة في موارد يدعمها التطبيق.
- وضع `--web` مربوط بـ`127.0.0.1`، لكن هذا لا يغني عن حماية حساب Windows ومجلد البيانات. لا تفتح المنفذ أو تعرّض التطبيق للإنترنت دون تصميم ومراجعة أمنية منفصلة.
- تغيير كلمة مرور المدير يتطلب جلسة مدير صالحة، لكن النموذج الحالي لا يطلب كلمة المرور القديمة؛ حدّها الأدنى ستة أحرف.
- الإيصال بعرض CSS ثابت 280px وبخط نظام عربي/سانس، ولا يوفّر اختيارًا صريحًا لمقاس 58mm/80mm أو محاذاة monospace.
- التنبيه بالمخزون المنخفض يخص المواد، لا الكتب. بعض بيانات البذر تبدأ بمخزون أو تكلفة صفرية، والوصفة الفارغة للمشروب لا تستهلك مواد حتى تُضبط.
- يوجد جدول `purchases` وصلاحية موظف لإدارة المشتريات، لكن الإصدار الحالي لا يوفّر مسار API لإضافة سجلات شراء؛ لذلك لا تفترض أن صلاحية المشتريات تعني توفر شاشة تسجيل شراء.
- `slug` التصنيف معرّف داخلي ثابت؛ تغيير الاسم الظاهر لا يغيره.
- يوم لوحة المعلومات يبدأ حسابيًا عند 10:00 محليًا، بينما بعض التقارير اليومية تعتمد التاريخ التقويمي. راجع قسم التقارير قبل مطابقة الأرقام بين الشاشات.
- لا يوجد جدول مستقل للحضور أو تعديلات الرواتب اليومية؛ الحضور من الورديات والتسوية في `payroll_settlements`.

## 13. أعمال مستقبلية

هذه أفكار غير منفذة حاليًا، وليست ميزات متاحة:

- توسيع خيارات الثيم وتخصيص المظهر مع الحفاظ على لوحة ألوان العلامة التجارية.
- ربط الإضافات بسطر مشروب محدد كخيارات أو إضافات قابلة للتسعير، بدل بيعها كمنتجات تجزئة مستقلة فقط.
- حفظ إعدادات الراتب التاريخية لكل يوم أو فترة، حتى لا يعتمد الحساب التاريخي على راتب الموظف الحالي وحده.
- تحسين تنسيق الإيصال ليستخدم خطًا monospace لمحاذاة الأعمدة، وتوفير إعدادات واضحة لأحجام الطابعات الحرارية.
- استكمال توحيد الألوان والمسافات الصلبة المتبقية في CSS؛ هذه مهمة تنظيف مؤجلة وليست جزءًا من إعدادات ثيم ديناميكية.
- توسيع تغطية اختبارات تبديل أقسام الشريط الجانبي، وتصحيح اختبار تسجيل الخروج ليستخدم طريقة POST الفعلية.
